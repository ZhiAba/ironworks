只被炮塔消耗，**不参与任何合成**。

| 重头弹 | 重弹头，高单发伤害、低射速 |

## 三、已设计机制

### 3.1 桶装液体物流
```
挖冰机 → 冰块 → 融冰机 → 水 ─┐
                              ├→ 装桶机 → 水桶 ──→ 拆桶机 → 水（桶材消失）
```

## 五、阻塞点（必须决策）

1. **黑火药缺原料**：现实配方是 硝石 + 硫 + 炭，原版没有硫和硝石，也没有氮源。
2. **多配方工厂**：原版没有可切换配方的工厂基类，需要自己写。
3. **挖冰机**：冰是地形不是矿脉，`Drill` 无法直接采。

# MultiCrafterLib 逆向分析（2026-10-20）

## 实测：被遗弃版模组在 160.3 无头端可加载
`decay-mod-casing-press` 的电力状态：
- `hasPower = true`
- `consPower = mindustry.world.consumers.ConsumePower@...`（由 hjson 的 `consumes.power` 解析而来）
- `hasConsumers = true`，`powerCapacity = 0.0`

## 库的电力模型（字节码证据）
```java
// setupConsumers()
if(isConsumePower) consume(new ConsumePowerDynamic(b -> 当前配方.input.power));

// MultiCrafterBuild
float getCurPowerStore(){ return power == null ? 0 : power.status * powerCapacity; }
void  setCurPowerStore(float v){ power.status = Mathf.clamp(v / powerCapacity); }

// updateTile 里的门槛判断
if(efficiency > 0){
    if(hasPower && getCurPowerStore() < recipe.input.power) skip;   // 电不够就不做工
    ...
}
```
关键推论：
1. `hasPower == false` → **整段电力判断被跳过** → 无电也能工作（最典型的症状）
2. 没有任何配方写 `input.power` → `isConsumePower = false` → 不注册动态消耗器 → 电网收不到需求
3. `powerCapacity == 0` → 电量恒为 0 → 会导致**做不了工**（与原症状相反，可用来排除）

## 旧模组加载日志暴露的 4 个问题（教训）
1. 配方引用了不存在的物品 `decay-mod-titanium-bullet-head`（定义叫 `titanium-ammo`/`alloy-bullet-head`）
   → 内容名引用缺少校验，会静默跳过配方
2. `decay-mod-high-furnace` 不在科技树，但 `sheet-roller` 以它为前置 → 科技树断链
3. `electrolyzer` 与 vanilla 同名，触发 re-declare 警告
4. `catena.hjson` 的 `allowWaveSimulation` 字段在 160.3 已不存在 → **库/字段随版本漂移会静默失效**

# 自研 MultiCrafter（0.8.0）—— 已完成并在手机上验证

## 为什么自己写
旧库 `multicraft.MultiCrafter` 的电力模型有缺陷：
- `getCurPowerStore() = power.status * powerCapacity`，把「电网满足度」当成「电池电量」
- `powerCapacity` 默认 0，配方也不写 `input.power` 时，整条电力链路形同虚设
- 面板里写 `consumes: {power: N}` 与配方里的 `input.power` 是两套互不相通的机制

## 自研实现
`ironworks.multicraft.MultiCrafter extends Block`，核心三条：

```java
consume(new ConsumeItemDynamic  (b -> ((MultiCrafterBuild)b).recipe().inputs));
consume(new ConsumeLiquidsDynamic(b -> ((MultiCrafterBuild)b).recipe().liquidInputs));
consume(new ConsumePowerDynamic  (b -> ((MultiCrafterBuild)b).recipe().power));
```

- 电力走**原版动态消耗器**：电网每帧拿到的就是当前配方的真实功耗
- 配方索引用 `Block.config(Integer.class, ...)` 注册，存档由 `SaveVersion` 经 `TypeIO.writeObject(block.config)` 自动持久化
- 切换配方时 `progress = 0`，不会串味

## 实机验证（手机，160.3）
- 放置弹药组装机 → 点击 → 弹出 5 个配方按钮：
  `铜制弹药 / 重头弹 / 铅芯被甲弹 / 钛芯穿甲弹 / 钛超压穿甲弹`
- 无头端：`consPower = ConsumePowerDynamic`、`recipes.length = 5`、`consumers.length = 3`

## 尚未验证
- 配方按钮的选中高亮（刚加，未复跑）
- 存档再读档后配方索引是否保持（逻辑上依赖 `block.config`，未实测）

# 详情页配方表（0.8.1）

## 问题
`MultiCrafter extends Block` 而没重写 `setStats()`，导致方块详情页缺少「输入/输出」区块 ——
玩家在建之前看不到配方，建好也看不到产率。原版 `GenericCrafter` 自带这段，继承 `Block` 就丢了。

## 移植自原库的实现方式
反编译 `multicraft.MultiCrafter` 后确认它的做法：

```java
public void setStats(){
    super.setStats();
    stats.add(Stat.output, (StatValue)table -> buildStats(table));  // 只挂一个 StatValue
}
```
真正的表格在 **显示时现场拼**（`buildStats`），所以配方改动会立刻反映到详情页 —— 这就是「动态」的来源。

## 本项目实现
同样用 `StatValue` 现场拼表，并补上原库没做的两件事：
1. **每条配方显示名字**（`recipe.ironworks.<name>`），否则 5 行图标无法区分
2. **显示工时（秒）与功耗（/秒）**

布局：每条配方两行 ——
```
【配方名】
【输入图标】 → 【输出图标】  1.50s  ⚡120
```
图标用 `StatValues.stack(...)`，自带悬停提示（物品名 + 数量）。

## 验证状态
- 编译：通过
- 配置界面（放下去后切换配方）：**实机截图确认**，5 个按钮 + 当前配方高亮
- 详情页配方表：**仅编译通过，未实机截图确认**（操作时用户正在使用手机，反复切屏会打断）

# 0.10.x：桶材消耗 + 液体单位 bug + 多配方合并

## 1. 桶材消耗（按设计补上）
原设计：「共用封装工厂和**基础材料消耗**」「拆桶机→水（**桶材消失**）」。
修正后：
- 封装机：`液体 30 + 铜板 1 → 1 桶`
- 拆封机：`1 桶 → 液体 30`（桶材不回收）

## 2. 液体消耗单位 bug（重要）
`ConsumeLiquidsDynamic.update()` 的 amount 是**每 tick**：
`build.liquids.remove(stack.liquid, stack.amount * build.edelta() * mult);`
而配方里按「每 craft」书写，直接传会放大 60 倍（30 → 1800/秒）。

修法：注册消耗器时按 craftTime 折算：
`scaled[i] = new LiquidStack(src[i].liquid, src[i].amount / max(craftTime, 1f));`
物品输入无需折算（ConsumeItemDynamic.trigger 本来就是每次合成扣一次）。

## 3. 多配方合并
| 改前（4 个方块） | 改后（2 个方块） |
|---|---|
| 铜轧机 + 铅轧机 | 金属轧制机（2 配方） |
| 铜电解槽 + 铅电解槽 | 电解精炼槽（2 配方） |

脱硫塔、火药混合机也换成 MultiCrafter，详情页与配置界面统一。方块总数 464 → 462。

## 4. 数值调整
| 方块 | 液体消耗（每 craft） | 折算速率 |
|---|---|---|
| 电解精炼槽 | 水 15 | 12/秒 |
| 脱硫塔 | 石油 12 + 氢 6 | 12/秒 + 6/秒 |
| 火药混合机 | 氮 6 | 8/秒 |

- 两条精炼配方的水消耗均为 15

# 与原库 MultiCrafterLib 的对照（源码级）

仓库：https://github.com/liplum/MultiCrafterLib （经 ghfast.top 代理拉取 master 分支源码）

## 一致的部分
| 项 | 原库 | 本项目 |
|---|---|---|
| 电力 | `ConsumePowerDynamic(b -> b.getCurRecipe().input.power)` | 同 |
| 物品 | `ConsumeItemDynamic` | 同 |

## 不一致的部分
| 项 | 原库 | 本项目 | 影响 |
|---|---|---|---|
| 液体消耗单位 | `amount` 按**每 tick**（`ConsumeFluidDynamic.update` 里 `amount * edelta`） | 按**每 craft**，库内按 craftTime 折算成速率 | hjson 配方不可直接迁移 |

| 内容定义 | hjson 数据驱动（`MultiCrafterParser`） | Java 代码（类型安全） | 各有取舍 |

## 教训
原库的液体语义若被照抄，会把「每 craft 30 水」变成「每 tick 30 水」= 1800/秒，
**编译期与加载期都不会报错**，只会在游戏里表现为瞬间抽干管网。这类问题只能靠读源码 + 单位核算发现。

# 多维平衡模型（0.14.0）

用户指正：平衡不是只看 DPS，而是「**出现时期 × 造价 × 弹药消耗（速率 × 单位成本）**」的乘积。

## 工具
`tools/balance.js`：从基础资源递归展开整条生产链，算出每种弹药的「铜当量」单位成本，
再叠加射速得「成本/秒」，最后与 DPS 相除得到「每铜当量 DPS」作为效率参考。

## 推演发现的失衡（按严重度）

| 问题 | 数据 | 根因 |
|---|---|---|
| 黑火药太贵 | 16 铜当量/个 | 硫 19（12 油 + 6 氢才出 1 个） |
| 速射炮弹药成本爆炸 | 23 铜当量/秒，效率仅 4.5 | 上游贵 + 批量小 |
| 重头弹过于划算 | 效率 48 vs 铜弹 22 | 装填倍数高、射速慢 |
| 顶级弹药过强 | 钛超压效率 127 | 批量 2 + 装填 ×8 |

## 修正

| 项 | 旧 | 新 |
|---|---|---|
| 硫 | 12 油 + 6 氢 → 1 | 4 油 + 2 氢 → **2** |
| 黑火药 | 1 煤 + 1 硫 + 6 氮 → 2 | 1 煤 + 1 硫 + 3 氮 → **3** |
| 铜制弹药 | → 6 | → **8** |
| 重头弹 | → 3 | → **2** |
| 钛芯穿甲弹 | → 2 | → **1** |
| 钛超压穿甲弹 | → 2 | → **1** |

## 最终平衡表

| 炮塔 | 时期 | 造价 | 弹药 | 弹耗/秒 | 成本/秒 | DPS | 效率 |
|---|---|---|---|---|---|---|---|
| duo（原版） | T1 | 35 | 铜 | 1.5 | 1.5 | 27 | **18** |
| 速射炮 | T2 | 280 | 铜制弹药 | 7.5 | 5.5 | 120 | **22** |
| 速射炮 | T2 | 280 | 重头弹 | 1.3 | 5.2 | 125 | **24** |
| salvo（原版） | T3 | 400 | 硅 | 1.7 | 3.3 | 257 | **78** |
| 穿甲炮 | T3+ | 463 | 铅芯被甲弹 | 0.8 | 2.5 | 72 | **29** |
| 穿甲炮 | T3+ | 463 | 钛芯穿甲弹 | 0.5 | 2.4 | 101 | **43** |
| 穿甲炮 | T3+ | 463 | 钛超压穿甲弹 | 0.3 | 3.4 | 216 | **64** |

规律：
- 铜制弹药与重头弹效率接近（22 / 24），只是「持续输出 vs 单发爆发」的选择
- 高级弹药效率随档位递增（29 → 43 → 64），但仍低于原版 T3 的 salvo（78）
- 我方换取的是**射程**（300 vs 190）与穿透特性，符合「不可能三角」

## 局限（必须说明）
- 模型把钛、巨浪合金等稀有资源都折算成"铜当量"，**抹平了稀缺度差异**
- 没有计算工厂占地、耗电、物流压力
- 效用结论只对「单位时间资源消耗」成立，不代表实际战斗表现

| 想要的效果 | 引擎能不能做 | 依据 |
|---|---|---|
| 改自身的伤害/移速/装填/生命上限 | ✅ | `StatusEffect` 相乘字段（`damageMultiplier` 等） |
| 持续伤害、无视护甲伤害 | ✅ | `damage`（每 tick）、`intervalDamage` + `intervalDamagePierce` |
| 死亡时触发 | ✅ | 全局 `Events.on(UnitDestroyEvent)` |
| 改护甲值 | ⚠️ 只有动态状态 | `StatusEntry.armorOverride` 仅在 `effect.dynamic` 时读取 |
| **受到的伤害 +X%（易伤）** | ❌ | 没有 hook；`Unit.damage()` 直接结算 |

结论：「易伤」这类效果不做——与其硬做一个看起来能用、实际没生效的开关，
不如不实现。等以后真的需要时，用子弹侧补偿（例如额外结算一段 `Damage.damage`）。

## 四个状态

| 状态 | 效果 | 施加方式 |
|---|---|---|
| **腐蚀** corrosion | 每 30t 造成 12 点**破甲**伤害（24/秒），移速 ×0.85，装填 ×0.9 | 腐蚀弹（穿甲炮） |
| **纳米装甲** nano-armor | 每秒回复 4.2，移速 ×1.1，伤害 ×1.1，装填 ×0.9 | 纳米修复场（光环） |
| **玉碎** jade-shatter | 阵亡时爆裂：半径 44，60 点伤害，**只伤敌方** | 玉碎信标（光环） |
| **临界** critical | 伤害 ×1.5，移速 ×1.1，装填 ×1.15 | 临界装置（光环，仅残血单位） |

「自适应装甲」暂未实现：它的语义是「挨打后逐渐减伤」，而减伤正好落在引擎没有的
那个钩子上；做成「加血上限」只是纳米装甲的重复，没有设计价值。

## 腐蚀弹：为什么不做独立的「电解炮台」

大纲里写的是电解炮台 + 腐蚀弹。实际实现改成**穿甲炮的第 5 种弹药**，原因：

1. 炮塔已有两门，再开一门要重新过一遍「范围/伤害/射速」三角，边际收益低；
2. 穿甲炮的定位就是攻坚，腐蚀弹（破甲 + 迟缓）正好补它的功能性；
3. 弹药是独立大类，增加一种弹药的改动成本远小于增加一门炮。

配方：1 弹壳 + 1 钛板 + 2 硫 → 3 发（100t，3 电）。

## 战术支援方块

三个方块共用 `StatusAura` 基类（范围内友军单位每 tick 刷状态，耗电按 `useTime` 结算）。

| 方块 | 尺寸 | 范围 | 耗电 | 造价 | 说明 |
|---|---|---|---|---|---|
| 纳米修复场 | 3x3 | 10 格 | 8/s | 铅80 硅60 钛50 钢板20 | 回血 + 小幅增益 |
| 玉碎信标 | 3x3 | 8 格 | 5/s | 硅70 钛40 钢板30 | 阵亡爆裂 |
| 临界装置 | 3x3 | 9 格 | 6/s | 硅60 高纯铜40 钢板30 | 只对 <40% 血量的单位生效 |

平衡考虑：光环是「纯增益」，代价放在**电费**和**布点**上，不额外加弹药消耗。
临界装置额外加了血量门槛，避免变成无脑全员增伤。

| 炮塔 | 弹药 | 成本/秒 | DPS | 效率 |

## 两个踩坑（已写进 NOTES）

1. **3x3 的 `setBlock` 以点击格为中心**（`offset = -(size-1)/2`），
   并排放供电方块时会把它覆盖掉 —— 测试和电力布局都要按覆盖范围算。
2. **`Damage.damage` 对建筑的伤害是射线法结算**，一格墙会被多方向射线各打一次，
   实际建筑伤害约为标称值的 3~4 倍（60 标称 → 实测 200）。
   玉碎对建筑偏强，是按单位伤害 60 调的。

# 单位外挂装甲（0.17.0）

大纲里的机制：**单位可以外挂一种独立装甲，并获得与装甲对应的效果**。
这一版把它做成了「装甲块 + 装甲坞」的形状。

## 为什么能做「真实护甲」

上一批状态效果时确认过：`StatusEffect` 改不了护甲，`armorOverride` 只对动态状态生效。
但继续翻 `StatusComp` 发现它给了公开入口：

```java
/** Uses a dynamic status effect to override armor. */
public void statusArmor(float armor){
    applyDynamicStatus().armorOverride = armor;
}
```

于是外挂装甲可以真的**加一层护甲值**，而不是用「加血上限」糊弄。
`armorOverride` 是覆盖语义，所以装甲坞装的时候写成
`unit.statusArmor(unit.armor() + armorBonus)` —— 在单位自身护甲上叠加。

## 结构

| 类型 | 内容 |
|---|---|
| 物品 | 反应装甲块 / 复合装甲块 / 纳米装甲块（装备类，不是合成原料） |
| 方块 | 装甲压制机（2x2，3 配方，MultiCrafter）、外挂装甲坞（3x3，6 电） |
| 状态 | 反应装甲 / 复合装甲 / 纳米装甲块（都是永久状态） |

| 装甲 | 护甲 | 附带效果 | 造价（铜当量） | 定位 |
|---|---|---|---|---|
| 反应装甲 | **+8** | 生命 ×1.1，移速 ×0.9 | 4.1 | 便宜、最抗打、笨重 |
| 复合装甲 | +6 | 生命 ×1.2，装填 ×1.05，移速 ×0.95 | 7.0 | 贵，但机动损失小 |
| 纳米装甲块 | +3 | 回血 4.2/s，伤害 ×1.1，移速 ×1.1 | 4.0 | 廉价机动增强 |

## 规则

1. **一件一块**：装甲坞每给一个单位装上，就消耗 1 个装甲块；
2. **装上不脱落**：状态以 `Float.POSITIVE_INFINITY` 施加，单位阵亡才消失；
3. **一个单位只能穿一件**：装甲坞会跳过任何已带三种装甲状态之一的单位；
4. **可切换**：装甲坞带配置界面，三种装甲随时切，已装好的单位不受影响。

## 平衡思路

外挂装甲是**按单位计费的消耗品**（不像光环是持续电费），所以定价对标单位造价：
一个 dagger 的硅成本约 15，装一块反应装甲（4.1）相当于给单位加价 27%，
换来 8 点护甲（对 20 伤害的一发，实伤从 20 降到 11）。

反应装甲每点护甲最便宜，但移速 ×0.9 对近战/机动单位是真代价；
复合装甲贵一倍多，卖点是「几乎不损失机动」；
纳米装甲块走另一个方向——回复与输出，适合打完就走的单位。

## 实测（T11–T13）

| 用例 | 结果 |
|---|---|
| T11 装甲压制机 | 2 次合成 → 2 块反应装甲 |
| T12 装甲坞 | 对照组 20 伤害打成 20；穿上后 `armorOverride=8`，同样一击只掉 11 |
| T13 互斥 | 预装复合装甲的单位被跳过（`gotReactive=false`），计数不增加 |

## 一个测试陷阱

T13 第一版用 `apply(status, 1)` 给单位「预装」复合装甲，
结果 2 秒后状态已经过期，单位被正常装了反应装甲，测试误报。
**状态时长必须以 tick 计**——`1` 是一帧，不是一秒。

# 工厂合并与转炉热源（0.18.0）

## 一、同一种操作不该拆成两台机器

| 合并后 | 原来的方块 | 依据 |
|---|---|---|
| **轧机**（2x2） | 金属轧制机 + 轧机 | 都是压延成形，只是轧辊间距不同 |
| **电解车间**（2x2） | 电解池 + 电解精炼槽 | 都是电解槽，只换电解液 |
| **冲压机**（2x2） | 弹壳冲压机 + 弹头压制机 | 都是冲压成形 |
| **弹药组装机**（3x3，7 配方） | 弹药组装机 + 凝固汽油弹工坊 | 都是弹药总装/灌装 |

合并后科技树也跟着收：一台机器一个节点，不同产物挂在同一节点下面。

**没有合并的**：
- **高炉 / 氢还原炉**：反应器类型不同（焦炭竖炉 vs 氢气竖炉），温度和气氛差别很大，
  保留两条路线本身就是设计内容。
- **装甲压制机**：模具和吨位与子弹冲压不同，而且军事科技想单独成枝。

## 二、转炉的热量从哪来

原配方：`铁锭 + 氧气 → 钢锭`，耗 2 电。问题有两层：

1. **物理上**：冷生铁吹氧不会脱碳。转炉能工作，是因为进的是 1300℃ 的铁水，
   碳氧反应本身放热；拿室温铁锭去吹，只会把氧吹跑。
2. **游戏上**：要熔化就得有热源。用电加热在大前期不合理——
   那时候玩家连稳定电网都不一定有，却直接用电炉炼钢。

改法：**煤 2 + 铁锭 1 + 氧气 → 钢锭**，工时 100t，**不吃电**。
热量来自煤燃烧（熔化 + 保温），氧气只负责把碳氧化成 CO/CO₂。
方块描述也改成「先烧煤把生铁熔化，再向熔池顶吹氧气脱碳」。

代价是钢锭贵了 2 煤（铜当量 +2），穿甲炮造价 463 → 523。

## 三、电解车间里的水电解配方

液体输出按 **每 craft** 书写：`6 水 → 6 氢 + 3 氧`（60t，4 电）。

顺手补了 MultiCrafter 的一条 `shouldConsume`：**液体输出装不下就停工**，
否则多出来的氢氧会被直接吞掉，水白烧。

## 四、实测（T1–T14 全过）

| 用例 | 结果 |
|---|---|
| T3b 水电解 | 40 水 → 30 氢 + 15 氧（5 次合成，比例 2:1） |
| T6b 灌装合并 | 弹药组装机第 7 配方产出凝固汽油弹，石油桶被消耗 |
| T14 转炉 | 6 铁 + 12 煤 + 40 氧 → 3 钢锭；剩 3 铁 / 6 煤 / 25 氧；**无电可运行** |
| T1/T2 轧机 | 同一台轧机切配方出铜板、铅板 |

## 五、还剩什么可以合并（供后续判断）

- **装甲压制机 → 冲压机**：技术上可以并，但会让装甲解锁提前，且军事枝失去独立节点
- **高炉 + 氢还原炉 → 还原炉**：可以并成两配方，物理上略牵强（炉型不同）

这两条我没做，等用户判断。

# 真正的转炉：熔融金属链（0.19.0）

0.18.0 给转炉加煤是「先能用」的临时解。这一版把它换成真实的 BOF（氧气顶吹转炉）：
**进的是铁水，不是铁锭**。

## 链路

```
铁精矿 ──┐
         ├─ 高炉（焦炭）──→ 铁水 ──┐
煤 ──────┘                          ├─ 转炉（顶吹氧气）──→ 钢水 ──→ 连铸机 ──→ 钢锭 ──→ 轧机 ──→ 钢板
氧气 ───────────────────────────────┘

铁精矿 + 氢气 ──→ 氢还原炉 ──→ 海绵铁（铁锭）──→ 电弧炉（耗电 + 氧气）──→ 钢水 ──→ 连铸机 …
```

两条路线都汇到「钢水 → 连铸 → 钢锭」，区别在还原剂与热量来源：

| 路线 | 还原剂 | 热量来源 | 时代 |
|---|---|---|---|
| 高炉 → 转炉 | 焦炭 | 焦炭燃烧 + 熔体显热 + 碳氧反应放热 | 早/中期 |
| 氢还原 → 电弧炉 | 氢气 | **电** | 中/后期 |

这就是「电不能出现在大前期」的落地方式：早期炼钢靠化学能，电只在电弧炉这一环出现。

## 配方与流量

| 方块 | 配方 | 工时 |
|---|---|---|
| 高炉 | 2 铁精矿 + 2 煤 → **6 铁水** | 120t |
| 转炉 | 6 铁水 + 3 氧气 → **6 钢水** | 120t |
| 连铸机 | 6 钢水 → **2 钢锭** | 60t |
| 电弧炉 | 2 铁锭 + 2 氧气 + 6 电 → **6 钢水** | 120t |

流量对齐：高炉 3 铁水/秒，转炉也是 3 钢水/秒，正好一节拍；
氧气 1.5/秒 ≈ 一台电解车间的一半产能。

## 液体只能相邻输送

原版没有管道，液体只能靠方块相邻传递。所以这条链在布局上必须是
「高炉 | 转炉 | 连铸」挨着排。这是原版机制，不是我们的限制——
但也意味着产线布局会变成一条直线，玩家得规划空间。

科技树里**液体不能作为节点**（原版同样如此），所以铁水/钢水不会出现在研究界面，
只作为中间产物存在。

## 顺手修掉的一个库级 bug

转炉不需要电（配方 power = 0），但一放下去 `efficiency` 就是 0，原因：
`ConsumePowerDynamic` 的 `efficiency()` 直接返回 `build.power.status`，
没有接电网的方块 status 恒为 0，于是「不需要电的配方」反而被卡死。

修法：在 MultiCrafter 里覆写这个消费者的效率判断——

```java
consume(new ConsumePowerDynamic(b -> ((MultiCrafterBuild)b).recipe().power){
    @Override
    public float efficiency(Building build){
        return requestedPower(build) <= 0f ? 1f : super.efficiency(build);
    }
});
```

这个 bug 之前没暴露，是因为所有多配方方块的配方都要电。

## 实测（T14–T17）

| 用例 | 结果 |
|---|---|
| T15 高炉 | 8 铁精矿 + 8 煤 → 18 铁水，煤剩 2 |
| T14 转炉 | 40 铁水 + 30 氧 → 18 钢水（3 次合成），无需电网 |
| T16 连铸机 | 40 钢水 → 10 钢锭 |
| T17 电弧炉 | 4 铁锭 + 20 氧 + 电 → 12 钢水 |

平衡影响：钢锭成本下降，穿甲炮造价 523 → 484。

# 科技树按资源分级挂载（0.20.0）

## 问题

之前模组自建了一个独立根节点 `ironworks`。后果是：**解锁时期完全由模组内部链条决定，
和原版的资源分级脱节**——大前期的玩家就可能看到本该在三级材料时代才出现的钢铁线。

用户的要求很明确：同等级的资源，解锁时期要跟原版同等级资源对齐。
比如巨浪合金要在某个地图之后才解锁，那么跟它同级的模组资源也应该在相近的时候解锁。

## 做法：把子树挂到原版节点下面

不再用 `nodeRoot`，改成挂在原版科技树的现有节点上，**继承原版的前置研究与地图目标**：

| 模组分支 | 挂载锚点 | 对应时代 |
|---|---|---|
| 轧机 + 铜/铅/钛板 | `铅` lead | 二级材料 |
| 电解车间（氢氧 + 电解精炼） | `玻璃` metaglass | 二级材料 |
| 弹药线（脱硫→火药→冲压→组装→速射炮） | `硫磺炸药` pyratite | 火炸药 |
| 桶装物流 | `塑钢` plastanium | 石油线 |
| **钢铁全链**（磁选→高炉→转炉→连铸→钢板墙、氢还原→电弧炉） | **`巨浪合金` surgeAlloy** | 三级材料 |
| 穿甲炮 | 钢板节点下 | 三级材料 |
| 外挂装甲 / 战术支援 | `巨浪合金` | 三级材料 |

依据是用户自己定的材料分级表：**3 级 = 钢锭 / 钢板 / 巨浪合金**。
既然钢和巨浪合金同级，钢铁链就挂在巨浪合金节点下。

## 实现细节

原版内容先加载、模组后加载（`ContentLoader.createBaseContent()` → `createModContent()`），
所以模组 `loadContent()` 时 `Items.surgeAlloy.techNode` 已经存在，可以直接当父节点。

自动加载顺序这一点很关键：如果模组先加载，拿到的 `techNode` 会是 null。

构造子树时不能用 `TechTree.node()`（它依赖私有的静态 `context`），直接 new：

```java
static TechNode node(TechNode parent, UnlockableContent content){
    return new TechNode(parent, content, content.researchRequirements());
}
```

`TechNode` 构造器会自动把自己加进 `parent.children`，并生成依赖项的研究目标。
产物节点额外加一个 `Produce(content)` 目标，等价于原版的 `nodeProduce`。

## 验证

无头端打印父节点链：

```
blast-furnace  ← iron-concentrate ← separator ← surge-alloy
rolling-mill   ← lead
press          ← black-powder ← …（根节点 core-shard）
electrolysis   ← metaglass
armor-dock     ← nanite-plate ← armor-press ← surge-alloy
TechTree.all = 425，roots = 2（原版两个星球，模组不再另起根）
```

## 代价与取舍

- **模组不再有独立页签**：内容直接长在原版树上，按原版的节奏解锁。

# 修正材料分级模型（0.21.0）

0.20.0 我按「加工层数 = 等级」来挂科技树，把整条钢铁链挂到了巨浪合金下面。这个分法是错的。

## 用户给出的模型

> 加工层数 ≠ 物品等级，需要看它的下级材料是不是高等级材料。
> 铜：D 级 1 级；高纯铜：C 级 2 级；钛：C 级 1 级。
> 但不能说高纯铜 > 钛——这是多元化的分级，还要看材料的产品强度。

所以是**两条轴**：

- **字母档（D→C→B→A）**：获取难度 + 材料强度档位
- **数字层**：加工层数

同一档里层数高不代表更高级；不同档之间才有「谁更靠后」的关系。
高纯铜是 C 档 2 层，钛是 C 档 1 层，但它们**同档**，解锁时期应该接近，
而不是高纯铜更晚。

## 本模组材料的分级

| 材料 | 档 | 层 | 依据 |
|---|---|---|---|
| 沙 / 煤 / 铜 / 铅 / 水 | D | 1 | 直接采集 |
| 铁精矿 | D | 2 | 沙加工，本身不高级 |
| 铜板 / 铅板 | D | 2 | 压延 |
| 铁锭（海绵铁） | D | 3 | 还原，仍是常见铁 |
| 硫 | D | 2 | 脱硫副产 |
| 钛 | C | 1 | 原版稀有金属 |
| 高纯铜 / 高纯铅 | C | 2 | 电解提纯，纯度带来性能 |
| 钛板 | C | 2 | 压延 |
| 黑火药 / 弹壳 / 弹头 | C | 2 | 需要油、氮、精炼链 |
| 钢锭 | C | 2 | 原料是 D 档，但产品强度跨档 |
| 钢板 | C | 3 | 轧制 |
| 外挂装甲块 | B | 1 | 钢板+钛板+军用强度 |
| 战术支援方块 | B | — | 依赖钢板与钛板 |

注意「钢锭 = C 档」这个判断：它的原料（沙、煤）是 D 档，但钢的强度、
以及它对下游（装甲、炮塔）的支撑，把它推到了 C 档。所以它**不该跟巨浪合金（B 档）
一起解锁**，而应该与钛同代。

## 重新挂载

| 分支 | 锚点 | 档 |
|---|---|---|
| 轧机、铜/铅板 | 铅 | D |
| 磁选机、铁精矿 | 石墨 | D |
| 电解车间、高纯金属、氢还原炉、铁锭、电弧炉 | 玻璃 | C |
| 钛板 | 钛 | C |
| 弹药线（脱硫→火药→冲压→组装→速射炮） | 硫磺炸药 | C |
| **钢铁全链**（高炉→转炉→连铸→钢板→钢板墙、穿甲炮） | **钛** | C |
| 桶装物流、外挂装甲、战术支援 | 塑钢 | B |

与 0.20.0 的差别只有一处关键：钢铁链从巨浪合金（B 档）下移到钛（C 档），
理由是它的原料是 D 档，产品是 C 档——按用户给出的分级逻辑，它属于中期而不是后期。

# 查漏补缺（0.23.0）

不是加内容，是把「玩家真的会撞上、但测试没覆盖」的地方补掉。四个真 bug：

## 1. 两个方块没有贴图

合并工厂时改了内容名（`press`、`electrolysis-plant`），贴图还留在旧文件（`casing-press.png` 等）。
游戏里这两个方块会显示 "oh no" 占位图。

修法：补 `press.png`（取旧冲压机贴图）、`electrolysis-plant.png`（取旧电解槽贴图），
并删掉 10 张已删除方块的遗留贴图。

## 2. 存档后配方全变回第一个

`recipeIndex` 只存在内存里，没有写进存档。读档后所有多配方工厂回到配方 0。

原版可配置方块（比如分拣器）是自己重写 `write/read` 持久化的，`config()` 只用于蓝图与方块复制，
不参与存档。补法：

```java
@Override public byte version(){ return 1; }
@Override public void write(Writes write){ super.write(write); write.i(recipeIndex); }
@Override public void read(Reads read, byte revision){
    super.read(read, revision);
    if(revision >= 1) recipeIndex = Mathf.clamp(read.i(), 0, recipes.length - 1);
}
```

`version()` 是存档版本字节，旧存档是 0，读的时候跳过新字段，不会读坏。
装甲坞的 `armorIndex` 同样处理。

## 3. 液体产物会倒灌回上游

相邻的两台多配方机器会互相倒液体：连铸机把钢水倒给转炉，转炉的罐子被钢水占满，
铁水和氧气就进不来了 —— 整条线卡死。

两处修复：

1. `liquidOutputDirections`：液体只从指定两侧倒（0/2 = 左右），不再四面乱倒；
2. `acceptLiquid` 白名单：只接受**当前配方用得到的液体**，别的液体一概不收。

第二条比第一条更根本，即使方向配错也不会互相污染。

## 4. 液体容量判断写反了

为了防止产物被吞，我在 `shouldConsume` 里加了液体容量检查。第一版按**总量**算：

```java
float total = liquids.sum((l, a) -> a);
if(total + out.amount > liquidCapacity) return false;
```

结果转炉直接停摆：输入的铁水和氧气本身也占容量，40 + 30 就已经超过 60，
机器判定「没地方放产物」，永远不开工。

正确做法是只看**这一种产出液体**还能不能装下（和物品产出的判断一致）。
教训：容量是共享的，但判断要按产出物单独算。

## 回归

T1–T18 全过；T14 转炉在修复后恢复产出（18 钢水）。

# 科技树重做：两条独立线（0.24.0）

## 之前错在哪

0.22–0.23 我把模组节点挂在原版同级节点下面（铅、玻璃、钛、塑钢……）。
用户指出：挂在谁下面，就**必须先研究谁**。哪怕我们的内容时期相近、甚至应该更早，
也会被原版链子拖着走；而且物品节点默认没有研究成本（`Item` 的
`researchRequirements()` 返回空数组），等于免费解锁。

## 现在的做法

两条线都直接挂在**基础核心**（`Blocks.coreShard`）下，互不经过原版中间节点：

```
core-shard
├── 材料线：铁精矿 → 铜板 / 铅板 / 桶 / 钛板 / 高纯金属 / 铁锭 → 钢锭 → 钢板
│            └ 硫 → 黑火药 → 弹壳 → 弹头 → 七种弹药
│            └ 钢板 → 三种外挂装甲块
└── 建筑线：磁选机 → 轧机 / 电解车间 →(空气分离机 / 氢还原炉 → 电弧炉)
                     └ 高炉 → 转炉 → 连铸机
                     └ 脱硫塔 / 火药混合机 / 冲压机 → 弹药组装机 → 炮塔
                     └ 装桶机 / 装甲压制机 → 装甲坞 / 三种战术支援
```

解锁时期由**研究成本**决定，不再由父节点决定。

## 成本分级

物品节点过去是免费的，现在全部显式给数量。按时期分三档：

| 档 | 成本用到的资源 | 例子 |
|---|---|---|
| 早期（铜/铅/煤） | 铜、铅、煤 | 铁精矿 铜×150；铜板 铜×150；硫 煤×300 |
| 中期（硅/钛/玻璃） | 硅、钛、玻璃、石墨 | 钢锭 钛×200 硅×150 铅×150；弹壳 铜×250 铅×150 |
| 后期（自产钢材） | 钢板、钛板、高纯铜 | 穿甲炮 钢板×250 钛×400 硅×300；装甲坞 硅×400 钛×300 钢板×200 |

建筑节点同样显式给成本（不再依赖 `Block.researchRequirements()` 的自动推算），
早期建筑一两百资源、后期建筑四五百，和原版节奏接近。

## 仍然存在的依赖

- **材料线内部**：钢锭要铁锭、黑火药要硫——这是真实工艺依赖，不是人为排序。

# 矿脉与数据库可见性（0.25.0）

## 一、物品在数据库里整页消失的原因

用户报告：铁精矿在「物品源」和核心数据库里看不到，只能在建筑配方和模组内容列表里见到。

根因在数据库的过滤条件：

```java
(tab == Planets.sun || u.allDatabaseTabs || u.databaseTabs.contains(tab))
```

`databaseTabs` 是在 `postInit()` 里由 `shownPlanets` 拷贝来的。而 `shownPlanets`：

- **方块**：`Block.postInit()` 会根据建造材料自动推断所属行星（材料都在塞普罗 → 打塞普罗标签）；
- **物品 / 液体 / 状态**：没有任何自动推断，`shownPlanets` 永远是空集 → `databaseTabs` 为空
  → 在「塞普罗」页签下被整个过滤掉。

所以物品不是没注册，是被数据库的页签过滤掉了。建筑能正常出现，是因为方块有自动推断。

修复：给两条科技线根节点调用 `TechNode.addPlanet(Serpulo)`（会递归覆盖子树里的物品与方块），
再手动给三种液体和七个状态补塞普罗标签。

验证：`iron-concentrate` / `oxygen` / `corrosion` 的 `databaseTabs` 从 0 变成 1。

- 新方块 **铁矿脉**（`OreBlock`，名称 `iron-ore`），挖出来直接是铁精矿；
- 原版塞普罗的矿石清单写死在 `SerpuloPlanetGenerator.generate()` 的局部变量里，模组无法追加，

- 只影响**之后新生成**的区块，已有存档地形不变；
- 矿脉只铺在有地表、无建筑、无其他矿的格子上。

现在铁有两条来源：**矿脉直采** 与 **沙子磁选**。

# 转炉无法供料的恶性 bug（0.28.0）

用户实测：转炉完全不工作，怀疑「两种液体没有两个液体槽」。

## 真正的原因

我先查了 Mindustry 的液体容量语义：**容量是按每种液体单独算的**，
不是单一池子。`Building.dumpLiquid` 里的限制是
`liquidCapacity - liquids.get(liquid)`，两种液体各自可以占到容量上限，
所以「没有两个槽」这个判断并不成立——引擎本身就支持一个方块存多种液体。

真正的问题在这三处：

1. **液体输出被写成了定向的**。我给高炉/转炉/电弧炉/电解车间设了
   `liquidOutputDirections`，产物只从指定两侧流出。玩家把氧气源放在别的方向，
   氧气永远进不来，转炉自然不工作。
2. **部分方块没有液体白名单**。`GenericCrafter` 默认 `acceptLiquid` 什么都收，
   邻居会把不相干的液体（氧气、铁水）倒进来占满罐子。
3. **没有可视化**。定向输出在游戏里完全看不出来，玩家没法定点连接。

## 修法

1. **删掉所有 `liquidOutputDirections`**，液体从四面输出；
   安全性全部交给 `acceptLiquid` 白名单（见下）。
2. **所有带液体的方块统一走 MultiCrafter**，因为它的 `acceptLiquid` 只接受
   **当前配方用得到的液体**。这次把最后两个 `GenericCrafter` 也改了过来：
   - 氢还原炉：只收氢气
   - 空气分离机：没有液体输入，什么都不收
3. 方块描述补上「液体从相邻方块输入/输出」的提示。

## 排查结果

| 方块 | 液体 | 白名单 | 结论 |
|---|---|---|---|
| 电解车间 | 水进；氢氧出 | ✅ | 正常 |
| 空气分离机 | 无输入；氮氧出 | ✅（已改 MultiCrafter） | 正常 |
| 氢还原炉 | 氢进，水出 | ✅（已改 MultiCrafter） | 正常 |
| 高炉 | 铁水出 | ✅ 不收液体 | 正常 |
| 转炉 | 铁水+氧进；钢水出 | ✅ | 正常 |
| 连铸机 | 钢水/铁水进 | ✅ | 正常 |
| 电弧炉 | 氧/铁水进；钢水出 | ✅ | 正常 |
| 脱硫塔 | 油+氢进 | ✅ | 正常 |
| 火药混合机 | 氮进 | ✅ | 正常 |
| 装桶/倒桶机 | 液体进出 | ✅ | 正常 |

现在模组里已经没有 `GenericCrafter` 承载液体了。

## 回归测试（新增 T21/T22）

| 用例 | 结果 |
|---|---|
| T21 实战链路：高炉(左)喂铁水 + 空分(上)喂氧气 → 转炉 | 钢水 18，铁水 3，氧气 6 |
| T22 液体白名单：还原炉 | 收氢 true；收氧/铁水 false |

用例变多之后 120 秒会在跑到 T21 之前被砍掉，上一次没输出就是被这个截断的。

# 混料修复：多液体产出必须分口（0.29.0）

用户实测：空气分离同时产氮和氧，却没有分口。紧贴工厂的单个输出口会把两种液体一起
送进同一根管道/罐子，造成混料。

## 原因

上一版为了修转炉「氧气进不来」，我把所有 `liquidOutputDirections` 删了，
改成四面输出。对**单液体产出**没问题；对**同一配方产出两种液体**的方块就是灾难：
两种液体都往四面倒，邻居在最靠近的一侧同时收到氧和氮。

原版的做法本来是按**每种产出液体**单独指定方向：

```java
// GenericCrafter
int dir = liquidOutputDirections.length > i ? liquidOutputDirections[i] : -1;
if(dir != -1) dumpLiquid(outputLiquids[i].liquid, 2f, dir);
```

`i` 对应 `outputLiquids` 的下标，`-1` 表示四面。这才是正确语义——我上次理解成了
「整台方块一个方向表」。

## 修复

1. MultiCrafter 的 `liquidOutputDirections` 改为**按产出液体下标**取方向；
2. 多液体产出的两个方块显式分口：
   - 空气分离机：氮气 → 右（0），氧气 → 左（2）
   - 电解车间：氢气 → 右（0），氧气 → 左（2）
3. 单液体产出的方块（高炉铁水、转炉钢水、电弧炉钢水、还原炉水）保持四面输出，
   这样上一版修好的「相邻任意面都能接」仍然成立；
4. 出口方向补了**可视化**：在方块边缘画出对应液体颜色的短线+圆点，
   玩家能直接看出哪一侧出什么。

## 验证（T23 / T24）

| 用例 | 结果 |
|---|---|
| T23 空气分离，左右各接一个液体容器 | 右：氮 33 / 氧 0；左：氧 16 / 氮 0 |
| T24 电解水，左右各接一个液体容器 | 右：氢 33 / 氧 0；左：氧 17 / 氢 0 |

T1–T24 全过。

## 教训（补进排查规则）

- **一个配方产出多种液体 → 必须分方向**；单液体产出才可以四面乱倒。
- 改完代码要 **grep 验证目标行确实写进去了**：这次电解车间的方向行第一次没打上，
  脚本静默跳过，测试直接暴露（左罐收到的是氢）——如果只看「构建成功」就会漏掉。

## 一、多液体输出改回定向，但这次有图标

用户要求：多液体产出要像埃里克尔一样，放置/选中时能看到输出方向图标。

做法：

- 恢复所有液体产出方块的方向设置：

- 给 MultiCrafter 写了一个 `DrawLiquidOutputArrows` 抽屉：
  - 建成后：按**当前配方**的产出液体，在方块边缘画出该液体颜色的箭头；
  - **放置预览**：按配方 0 的产出画箭头（`drawPlanRegion` 转发给 drawer，和原版 GenericCrafter 同一路径）。
- 箭头是程序画出来的（箭杆 + 两翼），不依赖额外的贴图资源；
  原版的 `DrawLiquidOutputs` 需要 `<方块>-<液体>-output1/2` 贴图，我们的动态配方没法逐张提供。

上一版只有贴图上的短线，确实太不明显；现在是箭头 + 放置预览，和埃里克尔的观感一致。

## 二、炮塔水冷

用户指出炮塔没有液体槽、不能用水加速。

原版机制：`ConsumeCoolant` 是可选消耗器，`ReloadTurret.updateCooling()` 会按
冷却液热容把 `reloadCounter` 加速，倍率取 `coolantMultiplier = 5`。之前我们的炮塔
没设 `coolant`，所以既没有液体条也不能加速。

修复：

```java
liquidCapacity = 20f;
coolant = consumeCoolant(0.1f);   // 速射炮
liquidCapacity = 30f;
coolant = consumeCoolant(0.2f);   // 穿甲炮
```

- 接受水或低温液体（`ConsumeCoolant` 按温度与可燃性筛选）；
- 详情页会自动出现「冷却液」倍率条目；
- 描述里补了说明。

## 三、超速器是否有效

查了代码再实测：`Block.canOverdrive` 默认 true，超速器会对炮塔 `applyBoost`，
而炮塔装填走 `reloadCounter += delta() * ...`，`delta()` 含 `timeScale`——所以有效。

实测：超速器旁放速射炮，`timeScale = 1.5`。

# 定向输出的适用范围（0.31.0）

修正上一版的过度应用：只有**多液体产出**的工厂需要定向，单液体产出保持全向。

| 方块 | 产出液体 | 输出方式 | 箭头 |

# 迫击炮索敌：最密集敌群（0.34.0）

用户要求：索敌优先选射程内**敌人最密集处**，让溅射收益最大化。

## 实现

`MortarTurret` 不再用原版 `Units.bestTarget`（它只会按最近/最强挑单体），改为：

1. 收集射程内、盲区外、符合过滤条件的敌方**单位和建筑**到候选表；
2. 对每个候选，统计「以它为中心、半径 = 当前弹药的 `splashDamageRadius` 内有多少候选」；

这样迫击炮会自动往人堆里砸，而不是追着最前面那个跑。

# 循环冷却液系统（0.35.0）

## 实现范围（本轮）

设计文档里的一、二、六（石墨烯部分）先落地，其余章节见「未完成」。

## 两种离散液体

| 液体 | 角色 | 参数 |
|---|---|---|
| 石墨烯冷却液 | 冷液（输入） | 温度 0.2，热容 1.6 |
| 热冷却液 | 热液（输出） | 温度 0.95，热容 1.6 |

冷/热是两个独立注册的 Liquid，**不做连续温度仿真**，也不允许在同一管道里「混合」——
因为它们本来就是两种不同的液体，普通管道只会按液体类型各自存储。

## 循环闭环

```
石墨烯炉（石墨+氢+电 → 石墨烯）
        ↓
石墨烯流化机（石墨烯+水+电 → 冷液）
        ↓
炮塔（冷液进 → 装填加速 → 热液 1:1 出）
        ↓
冷却工厂（热液+水+电 → 冷液 1:1）
        ↺
```

## 炮塔侧：容器而不是单纯消耗器

`CoolantTurret extends ItemTurret`：

- `acceptLiquid` 只收**冷液**（热液只出不进，避免倒灌混料）；
- 每 tick 按 `coolantUse * delta()` 消耗冷液，同量 1:1 转成热液；
- 有冷液时装填额外加速（速射炮 ×1.7、穿甲炮 ×1.8）；
- 热液通过 `dumpLiquid` 从相邻方块排出——**只产出一种液体**，不存在多液体分口问题。

这里踩了一个坑：最初用 `edelta()` 计算流量，结果炮塔的 `efficiency` 在无目标时是 0，
冷液根本不消耗。改用 `delta()`（与效率无关）后正常。测试 T35 验证：冷液 20 → 6，热液 0 → 14。

## 石墨烯产线

- 石墨烯炉（2x2）：石墨 2 + 氢 4 + 电 3 → 石墨烯 1 / 60t
- 石墨烯流化机（2x2）：石墨烯 1 + 水 6 + 电 3 → 冷液 6 / 60t
- 冷却工厂（2x2）：热液 6 + 水 6 + 电 2 → 冷液 6 / 60t

| T32 石墨烯炉 | 3 石墨烯 |
| T33 流化机 | 24 冷液 |

# 酸与高温线（0.36.0）

## 酸（新液体）

- 制酸车间（2x2）：硫 2 + 水 6 + 电 2 → 酸 6 / 60t
- 用途一：**腐蚀弹**改用酸（原来用硫，逻辑不成立——硫是固体，做不出腐蚀性弹药）
- 用途二：**酸法石墨烯**，石墨烯炉第二配方：石墨 2 + 酸 4 + 电 2 → 石墨烯 1 / 45t（比氢法快）

## 普通管道拒收熔融金属

`Block.buildType` 是公开字段，可以在 `loadContent()` 末尾把原版 `conduit` / `liquid-junction` /
`liquid-router` 的建造类替换成匿名子类，重写 `acceptLiquid` 拒收熔融铁水/钢水。
`Block.init()` 只在 `buildType == null` 时自行推断，所以先设好就不会被覆盖。

- 普通管道：熔融金属 **false**，水 **true**（正常液体不受影响）
- 耐高温管道（`Conduit` 子类，碳化硅内衬 + 石墨电极 + 石墨）：熔融金属 **true**

这是「用规则引导行为」：不删原版管道，只是让它扛不住熔融金属，玩家自然会去造高温管道。

# 液体条跳闪与数据库丢失修复（0.38.0）

## 一、液体条来回跳

`Block.setBars()` 的默认逻辑：如果方块带液体、但**没有** `ConsumeLiquid` 消耗器，
它会加一条「动态液体条」——显示的是 `liquids.current()`，也就是**当前存量最多的那种液体**。

MultiCrafter 用的正是动态消耗器（`ConsumeLiquidsDynamic`），所以落进了这个分支：
罐子里冷液、热液交替成为最大值时，那一条条在两液体之间反复横跳，文字根本读不出来。

修复：

- `MultiCrafter.setBars()`：删掉动态条 `removeBar("liquid")`，改为按配方里出现的**每种液体**各加一条静态条；
- `CoolantTurret.setBars()`：同样删掉动态条，只留冷液/热液两条；
- `Crucible extends LiquidRouter`：删动态条，只显示熔融铁水/钢水两条，并且**只接受熔融金属**。

这样每条条只读自己的 `liquids.get(液体)`，互不干扰，也不会跳。

## 二、物品丢失：液体没进数据库

数据库按 `shownPlanets` 过滤。科技树只给两个根节点 `addPlanet`，而 `addPlanet` 会递归整棵子树，
所以物品/方块都覆盖到了；但**液体是单独列表**，之前只登记了氧气、铁水、钢水。

结果：酸、石墨烯冷却液、热冷却液在核心数据库里整页消失。

修复：液体列表补全为 6 种。headless 校验：所有 39 个物品、35 个方块、6 种液体的
`shownPlanets.size` 都是 1。

## 三、配方丢失：新配方插队打乱了旧存档索引

轧机原本是 铜板/铅板/钛板/钢板（index 3 = 钢板）。这次把铁板插在了钢板前面，
旧存档里 `recipeIndex = 3` 的轧机全部变成铁板——看起来就像「配方丢了」。

修复：铁板移到数组末尾（index 4），钢板保持 3。以后的规则：**新配方只能追加，不能插队**。
（高炉的碳化硅同理，一直放在熔融铁水之后。）

- T1–T46 全过；
- headless dump：19 个 MultiCrafter 方块的配方列表、39 个物品、6 种液体的数据库标签均正常。

# 炮塔冷却结算与闭环守恒（0.40.0）

## 一、炮塔冷却规则（按用户要求）

- **热液有上限**：不再无限堆积，最多到 `liquidCapacity`（40）；
- **热液满了**：停止消耗冷液，同时**失去冷液加速**，直到热液被排走；
- **只在锁定/开火时消耗**：`target != null || wasShooting || isShooting()`，不再空转；
- 冷液 → 热液严格 1:1，热液加不进去时就不消耗，绝不溢出。

实测（T43）：
- 无目标：冷液 20 不变，`cooling=false`；
- 出现目标：冷液 20→12、热液 8、`cooling=true`；
- 热液补满：`cooling=false`，冷液不再减少。

## 二、闭环「液体蒸发」的真实原因

复现：炮塔 + 冷却工厂 + 管道组成闭环，总液量从 40 一路掉到 0。

排查结论：**不是管道泄漏，是 MultiCrafter 的液体消耗模型错了**。

原版 `ConsumeLiquidsDynamic` 是 `update = true`，每 tick 按 `amount * edelta` 连续扣液体；
而产物只在 `craft()` 完成时一次性生成。于是：

1. 输入在中途断供时，已经扣掉的那部分液体**不会形成产物**——凭空消失；
2. `craft()` 触发时如果液体不够，`liquids.remove` 会被钳到 0，但产物照常生成——凭空出现。

一进一出两种误差叠加，闭环里的总量就飘了。

## 三、修法

1. 新增 `ConsumeLiquidsCraft`：`update = false`，只在 `craft()` 的 `consume()` 里按**每 craft 的整量**扣一次；
2. `craft()` 开始前校验物品和液体是否够整份，不够就不出货（进度保留，等料）；
3. 冷却工厂严格 1:1：30 热液 → 30 冷液，不多不少。

## 四、附带新增

- **冷却循环管道**：`Conduit` 子类，`leaks = false`。普通导管在断头处会把液体漏到地上，
  看起来同样像「蒸发」；闭环建议用这根。
- 炮塔冷却状态写进存档（revision 2）。

| T43a 无目标 | 冷液 20 不变，冷却关闭 |
| T43b 有目标 | 冷液 20→12、热液 8、加速开启 |
| T43c 热液满 | 加速关闭、冷液不再掉 |

# 通液带桥卡死：transportTime = 0 死循环（0.48.2）

用户放置通液带桥后游戏直接卡死（不崩溃，线程挂住）。全量日志器记录到卡死前最后一条
正是带桥的建造事件。

## 根因

`LiquidBeltBridge extends ItemBridge`，但没设 `transportTime`。
原版 `ItemBridge.transportTime` 默认是 **0**，而它的物品传输是这样的：

```java
public void updateTransport(Building other){
    transportCounter += edelta();
    while(transportCounter >= transportTime){   // transportTime == 0 → 永远成立
        ...
        transportCounter -= transportTime;      // 减 0，计数器不减
    }
}
```

`transportTime = 0` → `while(true)`，主线程直接挂死。这个问题只在**链接建立后**触发
（`updateTransport` 只在有有效 link 时调用），所以放置时没事，一连上就卡。

用 `kill -3` 抓线程栈确认：

```
at mindustry.world.modules.ItemModule.take
at mindustry.world.blocks.distribution.ItemBridge$ItemBridgeBuild.updateTransport
at ironworks.LiquidBeltBridge$LiquidBeltBridgeBuild.updateTile
```

## 修复

```java
transportTime = 4f;
```

T53：两座带桥建立链接 → 物品 1 个、水 5 单位正常跨格，服务器不再卡死。

```
tick=6908 dst=20.8816 src= 7.2174   ← 灌爆
```

预期是「前面的补到 15，后面的剩 13」，实际对岸被灌到 **20.88**。

## 根因

`LiquidBeltBridgeBuild.updateTile` 只检查了对岸的 `acceptLiquid`（小于容量就收），
但转账量 `liquidRate * delta` 没有按对岸剩余空间裁剪：

```java
float amount = Math.min(liquids.get(cur), liquidRate * delta());   // 没考虑 space
dest.handleLiquid(this, cur, amount);
```

对岸 14.9 时仍然会一次灌 0.4，于是每 tick 叠加、冲破 15 直到来源掏空。

## 修复

```java
float space = dest.block.liquidCapacity - dest.liquids.get(cur);
if(space <= 0.0001f) return;
float amount = Math.min(Math.min(liquids.get(cur), liquidRate * delta()), space);
```

## 验证

T54：两桥各 14 水，8 秒后 **来源 13 / 对岸 15**，正好是预期值。
T1–T61 全过。

# 0.53.0 原版材料闭环 + 铝全量

## 设计目标
1. 原版那批「有矿就能造」的材料，全部能在本模组的工业线里造出来，并且互相喂料；
2. 铝从矿到航空件是一条完整冶金链，不是一条占位配方；
3. 每条链都要有闭环点（副产物被另一条链吃掉），不做一次性消耗。

- **赤泥**：进废料分选厂提钍；
- **石墨电极**：石墨化炉（煤）+ 冲压机补齐。
