# 工程复盘与变更纪律

> 起因：3.8.2.2 返回主菜单时主星球/太阳系先放大再缩小，连续 5 个版本（3.8.2.3–3.8.2.7）
> 都在 FOV/zoom 锁上打补丁，直到回到 3.8.2.1 做基线对照，才在 3.8.2.9 一行插值里找到根因。
> 本文适用于所有功能：内容、数值、逻辑、存档、输入、渲染、UI，不只菜单美化。

## 一、这次错在哪

### 1. 把“已知修复”当成了事实
3.8.2.2 的 changelog 写的是“返回缩放连续、不再先瞬间放大”，于是后续版本默认
`returnOverlayHold` + `returnZoom` 是正确方向，只在它周围加锁、改 FOV、改恢复时机。
实际复查 3.8.2.1→3.8.2.2 的 diff 后才发现：**`returnZoom` 的线性插值本身就是放大来源**。

教训：changelog、旧注释、用户口述、上次结论都只是“线索”，不是“证据”。
定位前必须用 last-known-good / first-known-bad 两个真实版本做对照。

### 2. 用“症状层”的补丁代替“因果层”的定位
- 3.8.2.3：锁 60° FOV → 视角被拉远；
- 3.8.2.4：改成只临时锁天空盒 FOV；
- 3.8.2.5：返回保持阶段干脆不碰 FOV；
- 3.8.2.6：回退 3.8.2.2，只修天空盒；
- 3.8.2.7：在 `uiDrawBegin` 锁 zoom 目标。

每一版都在改“看起来最可疑的变量”，但没有一版先回答：
**FOV 和 zoom 在每一帧的数值关系是什么？屏幕尺寸由谁决定？**

### 3. 忽略了共享可变状态
`cam.fov`、`params.zoom`、`ui.planet.zoom`、`menuFov`、`params.uiAlpha` 都不是某一个
函数独占的。它们同时被 `updateMenuState()`、`PlanetDialog.act()`、`beginSkybox()`、
`endSkybox()`、`updateOverlay()` 读写。只要其中两个写入者的时序错开一帧，视觉就会
表现为“星球变大”“星空变大”“整个画面挤压”，但根因不在最后改的那个函数。

### 4. 真正根因其实很小
3.8.2.2 把 3.8.2.1 的：

```java
float zoom = menuZoom;
```

改成了：

```java
float zoom = Mathf.lerp(menuZoom, returnZoom, center);
```

FOV 按 `center` 从 60° 收到 12°，zoom 却线性回到 `returnZoom`（默认 1）。
中段 FOV 已收窄、相机仍太近，主星球和整个太阳系一起被放大；等 zoom 追上目标再缩回。
默认参数下 `center=0.5` 时屏幕角尺寸 0.548，菜单目标 0.433，**大约 27%**。

## 二、以后按这个流程做

### 第 1 步：固定基线，先复现
- 找到**最后一个正常版本**和**第一个异常版本**，记下准确 commit。
- 用同一设备、同一入口、同一操作步骤复现；录屏/日志/数值都行。
- 把“好”的定义写成可检查的句子，例如“返回全程主星球直径变化不超过 ±3%”，
  而不是“看起来不放大”。

### 第 2 步：做最小对照，不要凭记忆
- `git diff good bad -- <相关文件>`，把**每一个**改动列出来，不只列怀疑的那个。
- 对每个改动问三句：
  1. 它改变了哪个可观测值？
  2. 这个值还被谁读写？
  3. 它的变化有没有数学关系/时序依赖？
- 如果 diff 很大，先按“渲染/相机/UI/状态机/资源”分组，再逐组排除。

### 第 3 步：先找不变量，再写代码
优先找在过渡/结算/存档/输入过程中**应该保持不变**的量：
- 渲染：屏幕角尺寸、相机距离/FOV/zoom 的关系、NDC 坐标、像素包围盒；
- 逻辑：能量/物品/液体守恒、总伤害、波次计数、单位数量；
- 存档：读写前后字段一致、旧档可加载、缺省值可回退；
- 输入：同一手势在拖动/缩放/暂停前后的位移比例一致。

把不变量写成公式，检查起点、终点、极值、导数/单调性。不要用“先锁一下”“先延迟一帧”
掩盖还没理解的时序。

### 第 4 步：单变量实验
- 一次只改一个独立变量；如果必须同时改两个（例如 FOV 和 zoom），
  先推导它们的关系，再作为一个整体改动。
- 每个实验都能单独回滚；不要把“修复”“重构”“顺手优化”塞进同一版。
- 连续两版症状没改善，停止继续打补丁，回到第 1 步重新取基线。

### 第 5 步：保留无关修复，精确回退
“回退到上一个版本”只适合确认基线，不适合当最终方案。
3.8.2.2 里的覆盖层交叉淡化、其它星球淡出、横向挤压抑制是有效修复；
正确做法是保留它们，只替换坏掉的那一行/那一段，而不是整版回退。

### 第 6 步：验证要分层
- 无头测试：逻辑、数值、存档、API 兼容；
- 编译/加载：类加载、资源、桌面/Android 差异；
- 实机：GPU/UI/输入/帧时序，必须由用户或录屏确认；
- 明确写出“已验证什么、没验证什么”，不要把无头通过当成 UI 通过。

### 第 7 步：记录假设和反例
在 CHANGELOG / STATE / 本文档记录：
- 当时相信什么；
- 用什么证据推翻/确认；
- 哪条路走错了，为什么；
- 下次遇到同样症状先查哪里。

## 三、通用排障清单（任何功能）

1. **基线**：最后好/最先坏分别是哪个版本、哪个 commit？
2. **复现**：步骤、设备、帧率、入口是否固定？能不能稳定重现？
3. **指标**：有没有一个数值/日志/截图片段能判断“好/坏”，而不是凭感觉？
4. **共享状态**：这个值被哪些函数写？哪些函数读？事件顺序是什么？
5. **单位/坐标**：世界坐标/屏幕坐标、角度/弧度、tick/秒、FOV/zoom 是否混用？
6. **极值**：0、1、最大/最小 zoom、最小/最大分辨率、横竖屏、暂停/恢复、读档/重进。
7. **回滚**：把可疑 commit 单独 revert 后症状是否消失？不要一次回退五个。
8. **替代解释**：除了当前假设，还有哪两个原因能产生同样症状？怎么排除？
9. **改动面**：每一行改动都能解释“为什么必须在这里改”吗？
10. **兼容**：旧存档、多人、服务端/无头、两个客户端版本是否仍正常？

## 四、反模式清单

- “先锁一下 FOV/zoom/alpha 看看”——锁住的是症状，不是因果。
- “回退整个版本就干净了”——会丢掉有效的其它修复，并掩盖真正的坏改动。
- “changelog 说修好了，所以这里一定对”——changelog 是历史，不是证明。
- “无头测试过了，UI 就没问题”——无头不加载 GPU/PlanetDialog/输入。
- “只改一处，应该不会影响别的”——共享状态里没有“只改一处”。
- “加个延迟/下一帧再执行”——没搞清时序前，延迟只是把问题挪到另一帧。
- “一次改三个变量，总有一个能中”——中了也不知道是哪个，下次还会错。
- “用户说还有问题，就再换个参数”——连续两次无效就必须回到基线对照。

## 五、这次留下的具体技术结论

返回主菜单这条链路，后续改动先看这几条：

1. `PlanetRenderer` 的相机距离：
   `dist = (planet.radius + planet.camRadius) * camLength + (zoom - 1) * (planet.radius + planet.camRadius) * 2`。
   `zoom` 越大相机越远、星球越小；FOV 越窄星球越大。两者必须一起推导。
2. 返回过渡不要直接线性插值 `zoom`；按屏幕角尺寸插值，起点 `returnZoom`/60°，
   终点 `menuZoom`/当前 FOV，再反解 `zoom`。
3. `beginSkybox()`/`endSkybox()` 必须保存并恢复**绘制前真实的** `cam.fov`，
   不能恢复可能过期的 `menuFov`；返回保持阶段相机就是战役视角，FOV 应为 60°。
4. `PlanetDialog.act()` 每帧会写 `state.zoom` 和 `state.uiAlpha`；`updateMenuState()` 若也在写，
   必须保证两者目标一致，或明确谁在什么时候拥有写权限。
5. `Dialog.hide()` 的 `color.a < 0.99` 会触发整层 FBO 重绘；返回过渡要保持不透明，
   否则会出现横向挤压。这个修复与缩放/FOV 是独立问题，不要混在一起改。
6. 覆盖层交叉淡化、其它星球淡出、天空盒 FOV、星球 zoom 是四条独立链路；
   一次只动一条，分别记录验证结果。
